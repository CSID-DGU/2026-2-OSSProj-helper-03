> 공연 음성을 대본과 비교해 **배우가 지금 대본의 어디를 말하고 있는지**, 애드리브 뒤 **어느 큐로 돌아왔는지**를 자막 오퍼레이터의 보조 화면에 보여 줍니다.

## 1. 프로젝트 소개

### 배경

유니스텝은 뮤지컬·연극 공연에 외국인·청각장애인 관객을 위한 다국어 자막을 제공합니다. 자막은 공연 전에 번역·검수까지 끝나 있지만, **공연 중 한 줄씩 띄우는 일은 오퍼레이터가 전부 손으로** 합니다. 한 공연에 자막 큐가 약 1,000~1,500개입니다.

### 문제

- 배우가 애드리브를 하거나 대사를 건너뛰면 실제 대사가 대본과 달라집니다.
- 그 순간 오퍼레이터는 대본 위치를 놓치고, 다시 찾는 동안 자막이 비거나 **최대 30초까지 늦어집니다.**
- 공연과 캐스트가 3~4개월마다 바뀌어서, 새로 투입된 오퍼레이터는 애드리브에 익숙해질 때까지(4~5회차) 같은 어려움을 반복합니다.
- 음성인식으로 자막을 자동 송출하는 방식은 오류가 관객에게 그대로 보여서, 현장에서는 받아들이지 않습니다.

### 해결 방향

음성인식 결과를 **관객에게 보여 주지 않고**, 대본에서 현재 위치를 찾는 데만 씁니다.

1. 공연 음성을 인식해 대본 문장과 비교하고, 배우가 말하고 있는 **현재 큐**를 추적합니다.
2. 대본을 벗어나는 순간(누락·반복·애드리브)을 감지하고, 대본으로 돌아오면 **복귀 큐 번호**를 크게 표시합니다.
3. 결과는 오퍼레이터용 보조 화면에만 나타나고, 송출은 오퍼레이터가 기존 송출 프로그램에서 합니다.

## 2. 기존 방식과 달라지는 점

| 구분 | 기존 (유니스텝 현행 운영) | Helper 도입 후 |
|---|---|---|
| 자막 제작·번역 | 대본 변환 → AI 번역 → 사람 검수 | **변경 없음** |
| 자막 송출 | 오퍼레이터가 기존 송출 프로그램에서 수동 송출 | **변경 없음** (Helper에는 송출 기능이 없음) |
| 현재 대본 위치 | 오퍼레이터의 기억과 집중에 의존 | 보조 화면에 추정 위치와 신뢰도 표시 |
| 애드리브·대사 누락 | 위치를 놓치면 빈 자막, 다시 찾을 때까지 지연 | 이탈 알림 → 복귀 큐 번호 표시 |
| 기록 | 없음 | 회차별 이탈·복귀 로그(CSV 내보내기) |
| 필요 장비 | 오퍼레이터 노트북 | 같은 노트북 + 마이크(또는 콘솔 라인 입력) |

> 이 저장소의 코드는 모두 새로 작성합니다. 기존 송출 프로그램과 유니스텝의 자막 데이터는 수정하거나 저장소에 포함하지 않습니다.

## 3. 주요 기능

개발은 3단계로 나눠 진행합니다. **이번 학기 필수 목표는 1단계**이고, 2·3단계는 송출 프로그램 연동과 사회혁신가 동의 여부에 따라 진행합니다.

| 단계 | 기능 | 오퍼레이터 역할 |
|---|---|---|
| **1단계 (필수)** | 대본 위치 추적 · 이탈 감지 · 복귀 큐 표시 | 보조 화면을 보고 직접 송출 |
| **2단계 (연동 확인 시)** | 송출 중인 큐와 추정 위치의 차이 표시 | 차이를 보고 직접 송출 |
| **3단계 (연동·동의 시)** | 오퍼레이터가 켠 구간에서만 다음 큐로 자동 전진 | 켠 구간 외에는 직접 송출, 이상 시 즉시 수동 복귀 |

### 모듈

| 모듈 | 역할 | 단계 |
|---|---|---|
| ① 큐 시트 로더 | 자막 큐 파일을 읽어 대사·가사·음향·암전·안내 큐로 구분 | 1 |
| ② 오디오 입력 | 마이크 또는 콘솔 라인 입력, 음성 구간 검출(VAD) | 1 |
| ③ 음성인식 | 로컬(faster-whisper)과 클라우드 API를 비교해 10월 확정 | 1 |
| ④ 대본 정렬 엔진 | 현재 큐 주변에서 자모 단위 유사도로 위치·신뢰도 산출 | 1 |
| ⑤ 대본 이탈 감지 | 누락·반복·애드리브 분류, 복귀 큐 산출, 노래 구간·입력 끊김 시 알림 보류 | 1 |
| ⑥ 보조 화면 | 추정 위치, 이탈 알림, 복귀 큐 번호, 입력 상태 표시 | 1 |
| ⑦ 회차 로그 | 추정 위치·이탈·복귀 이벤트 기록 | 1 |
| ⑧ 송출 큐 연동 | 송출 프로그램의 현재 큐와 추정 위치 비교 | 2 |
| ⑨ 자동 전진 제어 | 켠 구간에서 신뢰도·연속 일치가 기준 이상일 때만 전진 | 3 |

## 4. 시스템 구성

별도 서버 없이 **오퍼레이터 노트북 한 대** 안에서 동작합니다. 로컬 서버(FastAPI)가 음성 처리와 정렬 엔진을 실행하고, 보조 화면(React)과 WebSocket으로 통신합니다.

```mermaid
flowchart LR
    MIC["🎤 무대 음성<br/>마이크 · 콘솔 라인"] --> AUD["② 오디오 입력<br/>VAD"]
    AUD --> STT["③ 음성인식"]
    CUE["📄 자막 큐 파일"] --> LOAD["① 큐 시트 로더"]
    STT --> ALIGN["④ 대본 정렬 엔진"]
    LOAD --> ALIGN
    ALIGN --> DEV["⑤ 대본 이탈 감지"]
    DEV --> UI["⑥ 보조 화면"]
    DEV --> LOG[("⑦ 회차 로그<br/>SQLite")]
    UI --> OP(("👤 오퍼레이터"))
    OP -->|직접 송출| TX["기존 송출 프로그램<br/>(변경 없음)"]
    TX -. "⑧ 2단계: 송출 큐" .-> UI
```

| 메시지 (WebSocket) | 방향 | 주요 필드 |
|---|---|---|
| `session.start` / `end` | 화면 → 엔진 | `show_id`, `cue_file` |
| `position.update` | 엔진 → 화면 | `cue_id`, `confidence`, `latency_ms` |
| `deviation.alert` | 엔진 → 화면 | `type`(누락·반복·애드리브), `since`, `return_cue_id` |
| `input.status` | 엔진 → 화면 | `audio_level`, `segment`(대사·노래) |
| `settings.update` | 화면 → 엔진 | `alert_threshold` |
| `cue.onair` (2단계) | 송출 프로그램 → 엔진 | `cue_id`, `sent_at` |

## 8. 설치 및 실행

> 🚧 **현재 기술 검증 단계라 실행 가능한 코드가 아직 없습니다.** 1단계 개발(7~10주차)이 끝나면 이 부분을 채웁니다.

배포 계획은 다음과 같습니다.

- **사용자(오퍼레이터):** GitHub Releases에서 설치 파일 하나를 받아 실행하면 브라우저에 보조 화면이 열리는 방식 (Windows 11 / macOS)
- **개발자:** Python 3.11 + Node.js 환경에서 엔진(`Src/`)과 보조 화면을 따로 실행, `pytest`로 테스트
- **권장 사양(초기 가정):** 4코어 이상 CPU, RAM 16GB, GPU 없이 동작 목표, USB 마이크 또는 오디오 인터페이스

## 11. 기여 방법

1. 작업 전에 이슈를 만들고 담당자를 지정합니다.
2. `main`에서 브랜치를 만들어 작업합니다. (예: `feat/align-engine`, `docs/readme`)
3. 커밋은 한 가지 변경만 담아 작게 나누고, 아래 형식을 지킵니다.
4. PR을 올리고 팀원 1명 이상의 리뷰를 받은 뒤 병합합니다.

**커밋 메시지 형식** — `타입: 무엇을 했는지`

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·설정·기타 작업 |

```
feat: 대본 정렬 엔진에 자모 단위 유사도 추가
docs: 제안 발표 수행계획서 PDF 추가
```
