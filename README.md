## 1. 프로젝트 소개

### 배경

유니스텝은 뮤지컬·연극 공연에 외국인과 청각장애인 관객을 위한 다국어 자막을 제공합니다. 자막은 공연 전에 번역과 검수가 끝나 있지만, 공연 중에 한 줄씩 띄우는 일은 오퍼레이터가 직접 합니다. 한 공연의 자막 큐는 약 1,000\~1,500개입니다.

### 문제

- 배우가 애드리브를 하거나 대사를 건너뛰면 실제 대사가 대본과 달라집니다.
- 이때 오퍼레이터가 대본 위치를 놓치면 다시 찾는 동안 자막이 비거나 늦어집니다. 보통 2\~3초, 길면 30초까지 늦어집니다.
- 공연과 캐스트가 3\~4개월마다 바뀌어서, 새로 들어온 오퍼레이터는 애드리브에 익숙해질 때까지(4\~5회차) 같은 어려움을 겪습니다.
- 음성인식 결과를 그대로 자막으로 내보내는 방식은 틀린 글자가 관객에게 보이기 때문에 현장에서 쓰지 않습니다.

### 해결 방향

음성인식 결과는 관객에게 보여 주지 않고, 대본에서 현재 위치를 찾는 데만 씁니다.

1. 공연 음성을 인식해 대본 문장과 비교하고, 배우가 말하고 있는 현재 큐를 추적합니다.
2. 대본을 벗어나는 순간(누락, 반복, 애드리브)을 감지하고, 대본으로 돌아오면 복귀 큐 번호를 표시합니다.
3. 결과는 오퍼레이터용 보조 화면에만 나오고, 송출은 오퍼레이터가 기존 송출 프로그램에서 합니다.

## 2. 기존 방식과 달라지는 점

| 구분 | 기존 (유니스텝 현재 운영) | Helper 사용 시 |
|---|---|---|
| 자막 제작·번역 | 대본 변환, AI 번역, 사람 검수 | 변경 없음 |
| 자막 송출 | 오퍼레이터가 기존 송출 프로그램에서 수동 송출 | 변경 없음 (Helper에는 송출 기능이 없음) |
| 현재 대본 위치 | 오퍼레이터가 기억과 집중으로 따라감 | 보조 화면에 추정 위치와 신뢰도 표시 |
| 애드리브·대사 누락 | 위치를 놓치면 빈 자막, 다시 찾을 때까지 지연 | 이탈 알림 후 복귀 큐 번호 표시 |
| 기록 | 없음 | 회차별 이탈·복귀 로그 (CSV 내보내기) |
| 필요 장비 | 오퍼레이터 노트북 | 같은 노트북 + 마이크 또는 콘솔 라인 입력 |

이 저장소의 코드는 모두 새로 작성합니다. 기존 송출 프로그램과 유니스텝의 자막 데이터는 수정하지 않고 저장소에도 올리지 않습니다.

## 3. 주요 기능

개발은 3단계로 나눕니다. 이번 학기 필수 목표는 1단계이고, 2단계와 3단계는 송출 프로그램 연동 가능 여부와 사회혁신가 동의에 따라 진행합니다.

<p align="center"><img src="Doc/images/roadmap_3steps.png" width="820" alt="3단계 로드맵"></p>

| 단계 | 기능 | 오퍼레이터 역할 |
|---|---|---|
| 1단계 (필수) | 대본 위치 추적, 이탈 감지, 복귀 큐 표시 | 보조 화면을 보고 직접 송출 |
| 2단계 (연동 확인 시) | 송출 중인 큐와 추정 위치의 차이 표시 | 차이를 보고 직접 송출 |
| 3단계 (연동·동의 시) | 오퍼레이터가 켠 구간에서만 다음 큐로 자동 전진 | 그 외 구간은 직접 송출, 이상 시 수동으로 전환 |

### 모듈

| 모듈 | 역할 | 단계 |
|---|---|---|
| ① 큐 시트 로더 | 자막 큐 파일을 읽어 대사·가사·음향·암전·안내 큐로 구분 | 1 |
| ② 오디오 입력 | 마이크 또는 콘솔 라인 입력, 음성 구간 검출(VAD) | 1 |
| ③ 음성인식 | 로컬(faster-whisper)과 클라우드 API를 비교해 10월에 결정 | 1 |
| ④ 대본 정렬 엔진 | 현재 큐 주변에서 자모 단위 유사도로 위치와 신뢰도 계산 | 1 |
| ⑤ 대본 이탈 감지 | 누락·반복·애드리브 구분, 복귀 큐 계산, 노래 구간이나 입력이 끊기면 알림 보류 | 1 |
| ⑥ 보조 화면 | 추정 위치, 이탈 알림, 복귀 큐 번호, 입력 상태 표시 | 1 |
| ⑦ 회차 로그 | 추정 위치, 이탈, 복귀 이벤트 기록 | 1 |
| ⑧ 송출 큐 연동 | 송출 프로그램의 현재 큐와 추정 위치 비교 | 2 |
| ⑨ 자동 전진 제어 | 켠 구간에서 신뢰도와 연속 일치가 기준 이상일 때만 전진 | 3 |

## 4. 시스템 구성

별도 서버 없이 오퍼레이터 노트북 한 대에서 동작합니다. 노트북 안의 로컬 서버(FastAPI)가 음성 처리와 정렬 엔진을 실행하고, 보조 화면(React)과 WebSocket으로 통신합니다.

<p align="center"><img src="Doc/images/system_architecture.png" width="820" alt="시스템 구성도"></p>
<p align="center"><sub>점선 안이 이 프로젝트에서 만드는 부분이고, 테두리 색은 개발 단계를 나타냅니다.</sub></p>

엔진과 화면 사이 메시지는 다음과 같습니다.

| 메시지 (WebSocket) | 방향 | 주요 필드 |
|---|---|---|
| `session.start` / `end` | 화면 → 엔진 | `show_id`, `cue_file` |
| `position.update` | 엔진 → 화면 | `cue_id`, `confidence`, `latency_ms` |
| `deviation.alert` | 엔진 → 화면 | `type`(누락·반복·애드리브), `since`, `return_cue_id` |
| `input.status` | 엔진 → 화면 | `audio_level`, `segment`(대사·노래) |
| `settings.update` | 화면 → 엔진 | `alert_threshold` |
| `cue.onair` (2단계) | 송출 프로그램 → 엔진 | `cue_id`, `sent_at` |

## 5. 기술 스택

## 8. 설치 및 실행

지금은 기술 검증 단계라 실행할 수 있는 코드가 아직 없습니다. 1단계 개발(7\~10주차)을 마치면 설치 방법을 적겠습니다.

배포 계획은 다음과 같습니다.

- 오퍼레이터: GitHub Releases에서 설치 파일을 받아 실행하면 브라우저에 보조 화면이 열리는 방식 (Windows 11, macOS)
- 개발자: Python 3.11과 Node.js 환경에서 엔진과 보조 화면을 따로 실행하고, `pytest`로 테스트
- 권장 사양(초기 가정): 4코어 이상 CPU, RAM 16GB, GPU 없이 동작하는 것이 목표, USB 마이크 또는 오디오 인터페이스

## 11. 기여 방법

1. 작업 전에 이슈를 만들고 담당자를 정합니다.
2. `main`에서 브랜치를 만들어 작업합니다. 예: `feat/align-engine`, `docs/readme`
3. 커밋은 한 가지 변경만 담도록 작게 나누고, 아래 형식으로 메시지를 씁니다.
4. PR을 올리고 팀원 1명 이상이 확인한 뒤 병합합니다.

커밋 메시지는 `타입: 한 일` 형식으로 씁니다.

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작은 그대로 두고 코드 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드, 설정 등 기타 작업 |

```
feat: 대본 정렬 엔진에 자모 단위 유사도 추가
docs: 제안 발표 수행계획서 PDF 추가
```
